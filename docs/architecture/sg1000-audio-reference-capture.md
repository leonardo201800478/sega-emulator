# SG-1000 audio reference capture and characterization

**Status:** measurement protocol; no SG-1000 console capture has been authenticated for this repository as of 2026-10-26. This document does not claim analog-output fidelity.

## Evidence collected

- The SG-1000 board documentation identifies IC14 as an SN76489 sound generator and routes audio output from pin 7 to the RF modulator. This establishes a useful board-level measurement point, but does not establish the full frequency response of the console output. See [RetroTechWiki: Sega SG-1000](https://retrotechwiki.com/Sega_SG-1000).
- SMS Power hosts [SN76489 TestRom (SG-1000)](https://www.smspower.org/Homebrew/SN76489TestRom-SG), designed to compare real hardware and emulators. Use its source and documentation to understand each test mode; do not assume undocumented test timing.
- An [SMS Power hardware discussion](https://www.smspower.org/forums/17191-SG1000HardwareQuestions) links a recording made while a discrete SN76489 and a Sega PSG played in parallel. It is useful for chip-variant comparisons, but the described setup is not evidence of a complete, unmodified SG-1000 console output. It must not be used as the console-level analog oracle.
- A [reverse-engineering project for the SN76489](https://github.com/rejunity/tt05-psg-sn76489) includes chip-level studies and oscilloscope references. These support investigation of the chip, not the output network of a particular SG-1000 revision.
- A VGM file is a sequence of register writes and timing commands, not an analog recording. A waveform rendered from VGM by an emulator or RTL model is not a real-hardware capture.

## Capture request for the hardware community

The following request can be posted to SMS Power or sent to a hardware owner. No forum post has been submitted by this repository workflow.

> I am validating the audio output of an SG-1000 emulator and would appreciate a reference capture from an original console.
>
> If possible, please identify the console model (SG-1000, SG-1000 II, or SC-3000), board revision, PSG marking (e.g. SN76489AN versus a later integrated Sega/Yamaha device), video region, and capture point. Please state whether the capture is from the console's normal audio/RF path, a direct tap from PSG pin 7, or a modified line output.
>
> The most useful material would be unprocessed, lossless PCM WAV (48 kHz or 96 kHz, 24-bit if available), with no normalization, noise reduction, EQ, denoising, compression, or automatic gain control. Please include the recording interface, input gain, any coupling capacitor/preamp, and whether the signal was taken before or after the RF modulator. A short silent baseline followed by a deterministic test sequence is helpful.
>
> If possible, run the SMS Power SN76489 TestRom for SG-1000 and identify the exact test/mode used. A ROM/homebrew test source or a public-domain synthetic test program is preferable to a commercial game. Please also provide a photo of the console/board and PSG marking if convenient. Do not include copyrighted ROM images.
>
> A capture from a direct PSG tap and a capture from the normal console output are both useful, but they answer different questions and must be labelled separately. A direct tap can characterize the chip; the normal output path characterizes the console output chain.

## Minimum capture metadata

Record these fields beside every reference file:

- Console model and board revision; PSG part marking and whether the chip is discrete or integrated.
- Test program and exact mode; register-write sequence or source revision where available.
- Capture point: PSG output pin, board output, RF demodulator, or modified line output.
- Sample rate, bit depth, channel count, interface/device, gain, coupling and all analog components in the path.
- Whether any DSP, normalization, resampling, filtering or lossy encoding was applied.
- Duration, silence/baseline interval, and any known timing offset.
- File SHA-256 and permission/provenance for repository use.

## Characterization that can proceed without a console capture

Use fixed, synthetic input vectors and retain the raw PCM generated by the emulator. Do not change the default sound in response to listening impressions alone.

1. **Digital signal tests:** use deterministic register writes for each tone channel, noise mode, volume transition, period 0/1, reset, and rapid changes. Record clock rate and the exact write timestamps. Check measured frequency, repeatability, and channel isolation.
2. **PSG FIR characterization:** calculate the 63-tap filter's impulse response, passband ripple, stopband attenuation, group delay, and step/DC response. Report values computed from the actual coefficients and include the script/test version. These are properties of our filter, not properties of Sega hardware.
3. **PCM resampler characterization:** test each supported source/destination rate pair for passband and stopband response, block-boundary invariance, startup/flush transients, DC preservation, and deterministic output. Do not conflate this Qt resampler with the PSG's own filter.
4. **Level metrics:** for every fixed vector, record peak, RMS, mean/DC, clipping count, frequency estimate, and spectrum using a documented window and measurement interval. Normalize only for an explicitly labelled shape-only comparison; preserve absolute-level comparisons separately.
5. **Variant separation:** keep the SG-1000 discrete SN76489AN profile separate from later Sega/Yamaha integrated PSGs. Chip-level SN76489 evidence must not silently become a model of the complete console.
6. **Analog model policy:** do not add a guessed low-pass cutoff, high-pass/DC-decay constant, gain, or clipping curve to the default profile. If experiments are added, put them behind an explicitly experimental profile with documented parameters and no claim of hardware validation.

## Acceptance criteria

- Fixed vectors and measurement code are deterministic across repeated runs.
- Frequency, level, DC, spectrum, filter response and latency are emitted as machine-readable test results or stable assertions.
- Filter/resampler thresholds are defined from the implemented DSP requirements and independently checked; they are not described as measured SG-1000 properties.
- A real-hardware comparison is labelled **BLOCKED** until a provenance-documented capture from a known console/revision and known signal path is available.
- Any later analog parameter has either a cited schematic/component derivation or a measurement-backed fit with uncertainty. Otherwise it remains a hypothesis and is opt-in only.

## Current limitation

Public sources found so far provide chip-level evidence and a comparative hardware recording, but not a verified, unprocessed capture of the normal output of a known SG-1000 board running a reproducible test. Consequently, this protocol improves the evidence and testability of the digital/DSP pipeline but cannot close analog-output validation by itself.
