### 2.1 CPU checkpoint capability

**SG-1000:** the PyO3 `NativeCpuSnapshot` currently exposes primary registers, alternate AF/BC/DE/HL, IX/IY, I/R, IFF1/IFF2, interrupt mode, HALT, WZ, Q/P and total T-states. The wrapper's instruction counter is exposed separately. The underlying Z80 state and `Z80CpuSnapshot` type contain additional information such as EI delay and pending interrupt state, but these are not all exposed by the current Python snapshot.

**SMS:** the current PyO3 machine exposes PC, total instructions and total T-states, but does not expose a complete CPU register snapshot. The native `SmsMachine::cpu()` accessor exists in Rust, so a native read-only checkpoint can be added without moving CPU logic to Python.

**Conclusion:** complete, equivalent SG-1000/SMS CPU checkpoint support is **INTEGRATION_PENDING**. The contract correctly requires unavailable fields to be reported rather than synthesized. A future API should expose one explicit versioned snapshot shape for both systems, with stable-boundary semantics documented.

### 2.2 Video/framebuffer capability

**SG-1000:** the PyO3 VDP snapshot copies VRAM and framebuffer into owned `Vec<u8>` values; its Python getters create `PyBytes`. The current snapshot therefore performs copies and is not a zero-copy borrowed slice.

**SMS:** the native VDP exposes `framebuffer() -> &[u8]`; the PyO3 getter returns a `PyBytes`, which copies the framebuffer. The current SMS framebuffer is RGB24, 256 pixels wide, with visible height dependent on the VDP mode (192/224/240 lines). The Python adapter exposes framebuffer bytes, frame number and visible height.

**Conclusion:** framebuffer capture is **partially IMPLEMENTED**, but a shared raw-buffer descriptor (format, width, height, stride, visible region, frame number) is not yet exposed as a stable diagnostics contract. The current Python path copies data. The capture harness must not claim zero-copy behavior; a later Rust API may provide a scoped buffer/view or an explicit owned snapshot with documented allocation and lifetime.

### 2.3 Audio/PCM capability

Both PyO3 machine wrappers explicitly state that PCM is not returned to Python. Their frame execution drains native PSG samples into the Rust audio session, which mixes/resamples and writes PCM16 to the selected host sink.

At the Rust machine layer, SMS exposes `drain_audio_samples()` returning generated mono `f64` samples. The shared audio runtime's resampler produces PCM16 little-endian byte blocks, but the current `PcmSink` interface sends those blocks to the host output and does not expose a capture/recording sink through the machine diagnostics API. The inspected SG-1000 path follows the same host-output pattern.

**Conclusion:** deterministic PCM artifact capture is **NOT IMPLEMENTED at the public machine/FFI diagnostics boundary**. VGM write-event recording is not PCM. The follow-up should add an optional Rust-owned recording sink or a bounded PCM drain API at the correct point in the DSP pipeline, with sample format/rate/channel metadata and without a Python callback per sample. Do not route audio synthesis or mixing through Python.

### 2.4 Replay and stepping

Both native machine wrappers expose instruction stepping and frame stepping. The Python adapters expose controller state setters/masks. This is sufficient to prototype frame-boundary replay, provided each event records complete normalized input state and the exact frame application point.

It does not provide sub-frame timestamped electrical input replay or a scheduler-time event API. The contract's explicit frame-boundary limitation is therefore necessary and accurate.

### 2.5 Temporal/fidelity boundary

The inspected SG-1000 and SMS machine implementations advance VDP/PSG around completed Z80 instructions and describe the result as nominal instruction timing, not cycle-exact bus scheduling. The current APIs therefore support deterministic instruction/frame-level captures but cannot substantiate a claim of complete cycle-accurate machine timing or `TEMPORAL_PASS`.
