## Symptom under investigation

Manual comparison reported by the user: when viewing the image as an 8×8 grid, a horizontal pixel row appears to jitter vertically within column F in Ares this is not observed; a similar effect appears in column D in GearSystem. This description is a user observation, not yet an independently reproduced trace. The exact ROM/test, region, VDP revision, display mode, frame capture method, and whether the moving row is generated by mid-frame writes or intended raster behavior remain to be confirmed.

## Repository state and current implementation

The active SMS VDP is `native/sms_core/src/vdp.rs` on Rust `main`.

- `SmsVdp::advance(tstates)` accumulates T-states to a scanline boundary.
- `complete_scanline()` invokes `render_scanline(..., &self.cram, ...)` after a complete line. Rendering reads the then-current VRAM, CRAM, and registers for the whole line.
- `write_data()` updates CRAM immediately when CRAM write mode is active, but the framebuffer for an already rendered line is not revisited. Conversely, writes that happen before `complete_scanline()` may affect the entire line, regardless of the actual horizontal position of the write.
- The file itself states the model is deterministic and scanline-based, not dot-cycle exact.

This creates a specific temporal limitation: state changes during an active line are not represented at their horizontal pixel boundary. It is a plausible cause only if the test relies on mid-line changes; it is not yet proven to explain the reported column F/D symptom.

## Three investigation tracks

### Track A — MAME: Sega 315-5124 implementation

Sources:
- https://github.com/mamedev/mame/blob/master/src/devices/video/315_5124.cpp
- https://github.com/mamedev/mame/blob/master/src/devices/video/315_5124.h

Observed in the inspected source:
- MAME models the SMS/GG VDP as the `sega315_5124_device`.
- It schedules explicit timers for display/line processing, HINT/VINT, left/right borders, pending flags, and `draw_scanline`.
- `draw_scanline()` calls `update_palette()` and then draws a line buffer for the selected mode.
- `cram_write()` updates CRAM and marks the palette dirty; palette conversion is refreshed when the renderer updates it.

Interpretation:
- This is a line-timed raster architecture with more explicit scheduling than our current instruction-batched scanline boundary.
- The inspected path does not by itself prove arbitrary mid-line CRAM changes are rendered at the exact write pixel. Do not describe MAME as pixel-exact based only on these findings.
- Follow-up: inspect timer scheduling relative to Z80 writes, line-buffer composition and known SMS raster-effect tests.

### Track B — MEKA: line renderer and latches

Sources:
- https://github.com/ocornut/meka/blob/master/meka/srcs/video_m5.cpp
- https://github.com/ocornut/meka/blob/master/meka/srcs/video_m5.h
- https://github.com/ocornut/meka/blob/master/meka/meka.txt

Observed:
- `Refresh_Line_5()` targets the current VDP line, draws the background, then sprites, then applies the left-column mask.
- `Display_BackGround_Line_5()` uses latched horizontal and vertical scroll state and documents the SMS scrolling test for leading fine-scroll pixels.
- MEKA's project documentation advertises line-based raster effects, scroll handling, sprite collision and VDP variation emulation.

Interpretation:
- MEKA explicitly models per-line rendering state and scroll latches. The inspected rendering routine writes a line buffer rather than rendering each pixel in global time.
- Its existence of “line-based raster effect” support does not establish arbitrary horizontal sub-line precision. Follow-up: trace when `Refresh_Line_5` is called relative to CPU I/O writes and inspect the raster test behavior.

### Track C — GearSystem and Ares comparison

Sources:
- https://github.com/drhelius/Gearsystem/blob/master/src/Video.cpp
- https://github.com/drhelius/Gearsystem/blob/master/src/Video.h
- https://github.com/ares-emulator/ares/blob/master/ares/ms/vdp/vdp.cpp
- https://github.com/ares-emulator/ares/blob/master/ares/ms/vdp/io.cpp
- https://github.com/ares-emulator/ares/blob/master/ares/ms/vdp/background.cpp
- https://github.com/ares-emulator/ares/blob/master/ares/ms/vdp/dac.cpp

GearSystem findings:
- `Video::Tick(clockCycles)` advances line/cycle state and calls `ScanLine(m_iRenderLine)` when its configured render threshold is reached.
- `ScanLine()` dispatches to background and sprite renderers. CRAM writes are handled immediately in the VDP write path, but the inspected output path is line-based.
- Therefore, a CRAM mutation does not automatically imply that pixels already drawn on that line will be revised. The exact write/render ordering must be traced.

Ares findings:
- `VDP::main()` calls background/sprite setup for the line, then loops across 256 horizontal positions. For each x it runs background, sprite and DAC, then advances the VDP by two clocks and synchronizes with the CPU.
- SMS CRAM writes store the six-bit value immediately in `io.cpp`; `dac.cpp` resolves the palette as each output pixel is generated.
- This creates a finer-grained CPU/VDP interleaving point than the scanline render calls found in the inspected GearSystem and MEKA paths. This is a meaningful architectural distinction, but it is not proof that every VDP event is cycle-exact or that it alone explains the observed image.

## Current hypothesis (not yet confirmed)

The main architectural candidate is event ordering and horizontal granularity: our renderer snapshots the visible line only at its end, while Ares interleaves rendering with VDP clock advancement across horizontal pixel positions. If the test writes VDP registers/CRAM or changes state through an interrupt during the active line, the implementations may differ in where the change first appears.

Other plausible causes that must remain open:
- line interrupt counter phase or IRQ acknowledgment timing;
- register latch rules (especially scroll and display-related registers);
- CPU instruction-level T-state accounting and I/O write timestamp;
- region, VDP revision, frame pacing, capture/display scaling or a test that intentionally exploits hardware behavior;
- a defect in one emulator rather than a fidelity difference.

## Acceptance criteria before implementation

1. Reproduce the symptom with a legally obtained homebrew/synthetic test or a minimal deterministic ROM; record ROM/test identity without committing commercial ROMs.
2. Capture lossless native-resolution frames from Ares, GearSystem and our emulator using the same region, mode, scale and frame phase.
3. Determine whether the test performs mid-line writes. Record CPU T-state, scanline, horizontal phase, port/register/address and value for each relevant event.
4. Build a deterministic Rust regression that asserts the exact pixel transition / per-line output, not a visual subjective score.
5. Use MAME, MEKA, Ares and hardware documentation as independent comparative evidence while accounting for shared ancestry and differing implementation goals.
6. Implement only the smallest required temporal slice. Do not claim dot/cycle accuracy until bus access, waits, interrupts and event ordering are covered and validated.
