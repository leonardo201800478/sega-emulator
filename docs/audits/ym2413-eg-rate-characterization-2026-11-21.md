## Correct interpretation of the replay counts

The trace adapter `tools/ym2413-nuked-oracle/trace.c` calls
`OPLL_Reset` and `OPLL_Clock` from the pinned Nuked-OPLL source. The
38-configuration matrix is generated by writing the register fixtures into
that software oracle. The `eg_hardware_trace.rs` example explicitly
describes its input as pre/post Nuked trace samples.

Therefore the workflow's field name
`total_hardware_operator_samples` is a misleading label if read as
physical-chip capture. These 506,768 samples are **Rust EnvelopeOperator
replays against Nuked-generated pre/post state**, not 506,768 independent
YM2413 silicon measurements. Their zero mismatches establish exact replay
of the selected Nuked operator trace, not physical hardware validation.

Likewise:
- 1,140,000 EG sequencer calls: exact register-derived replay against the
  pinned Nuked trace, with zero field mismatches.
- 1,140,000 EG timer calls: replay against consumed Nuked timer latches,
  with zero field mismatches.
- 38 configurations x 6,418 selected operator samples = 243,884 samples
  in the rate-matrix comparison.

These are valuable software differential and pipeline-isolation results.
They must not be described as independent physical-chip captures.

## Why the zero-mismatch external-rate candidate is not evidence of a fix

The source `native/ym2413/examples/eg_model_trace.rs` explicitly implements
`seeded_external_rate_phase` as follows:

1. For each selected slot, initialize a Rust EG generator from the first
   observed Nuked `eg_level` and `eg_state` after DAMP.
2. Exclude that seed row from comparison.
3. For every subsequent update, call `tick_with_rate_phase` with
   `EnvelopeRatePhase` reconstructed from the consumed rate-phase latches
   extracted from the Nuked trace.

The extractor `tools/ym2413-nuked-oracle/extract_eg_samples.py` obtains
those consumed rate-phase values by reading the previous Nuked trace row's
`eg_rate_hi`, `eg_inc_lo`, `eg_inc_hi`, `eg_maxrate` and
`eg_counter_state_prev`. Thus the candidate is teacher-forced with internal
oracle state and oracle-derived rate latches.

It compares 6,410 of 6,418 samples per configuration: eight seed rows are
excluded per configuration, or 304 across the 38 configurations. The
zero-mismatch result is expected for a useful isolation harness, but it is
not independent validation, not a production algorithm, and not evidence
that the Rust global timer can generate those latches correctly.

**Do not promote `seeded_external_rate_phase` into production.** Its value
is to show that the per-operator EG update can reproduce Nuked when supplied
with Nuked's consumed rate phase and initial state. The remaining problem is
the independently generated global rate-phase/timer pipeline.

## Hardware evidence boundary

This workflow contains no physical YM2413 capture source. Its input traces
are generated from the pinned Nuked software oracle and its fixtures. The
andete measurements previously reviewed remain separate external
reverse-engineering evidence, but they are not part of artifact #14713567996.

Consequently, this run does not close:
- the physical EG rate-phase schedule;
- the physical reset/initial EG state;
- the relationship between the rate timer and serial slot phase;
- the SD rhythm SL candidate disagreement;
- any analog envelope or output behavior.

## Engineering decision

1. Keep production EG code unchanged.
2. Keep the 44,064/71 phase-minus-three candidate mismatch visible.
3. Treat the 243,580/0 external-rate replay strictly as oracle-fed isolation.
4. Do not label the 506,768 operator samples as physical hardware captures.
5. Next EG work must isolate the Rust-owned timer/rate-latch generation against
   oracle traces without injecting oracle latches into the Rust production
   candidate. Any new candidate must also preserve existing sequencer and
   timer replay results.
6. Continue FM-5.3 output-service work independently; this EG characterization
   does not provide the missing operator-to-raw-DAC mapping.
